# Upstream check and upgrade, 2026-09-17

Previous check: [upstream-2026-09-11.md](upstream-2026-09-11.md), which ended on
"keep the pin, watch for the next mlx-vlm release". The release came on 09-14 —
and turned out to be the one version of mlx-vlm this setup cannot run. This is
the record of the upgrade that followed.

State before: `mlx-vlm 0.7.0`, eight patches applied, `mlx 0.32.2`.
State after: **`mlx-vlm` main @ `548b09b`**, seven patches applied, `mlx 0.32.2`.

mlx PR `#4416` (head_dim 256 with an array mask through the default dispatch) has
been merged since 09-02 but is in no release, so patch `0013` stays needed in
full.

## Why the 0.7.1 tag is unusable here: #2259

The tag carries `#2182` (the APC redesign) but not its fix `#2262`.

`#2182` sized the prefill reserve from `_bytes_per_token`, computed as
`max(previous, snapshot_bytes / token_count)` — a **monotonic maximum over the
process lifetime**. A snapshot of a hybrid model contains the fixed GDN
recurrent state and unused KV capacity, neither of which scales with tokens, so
a short prompt produces an enormous bytes/token ratio. `prepare_prefill` then
reserved `2 · n · bytes_per_token`, `_make_room` failed for every long prompt,
and exact APC stopped storing **and** restoring for the rest of the process.

The reporter's numbers (M3 Max, 96 GB, Qwen3.8-27B-8bit + MTP): a 37-token
request set ≈4.05 MiB/token where a 5.9K-token snapshot had just produced
≈0.38 MiB/token; a 5,942-token prefill then reserved 48.1 GiB against 44 GiB of
headroom. Signature: `exact_stores` flat, `memory_skips` climbing, `cached_tokens`
0 on a repeated prompt, and a restart fixes it until the next short request.

**This is our traffic exactly.** Three pi instances sending short agent turns
between long ones; a prefix cache that dies minutes after startup, silently,
would have cost 2–3 minutes of cold prefill per 30k conversation.

`#2262` (merged 2026-09-16, in no tag) removes the mechanism rather than tuning
it: `_bytes_per_token`, `_cache_size_estimate` and both proportional
exact-restore estimates are deleted, and planning runs through the cache
adapters with real tensor dimensions. Verified here — none of those three
symbols exists in `apc.py` on `548b09b`.

### Verified after the upgrade

The scenario from the issue, against the running server:

| step | prompt | `cached_tokens` | wall |
|---|---|---|---|
| 1 | 19 tokens (the poisoner) | 0 | 3.48 s |
| 2 | 5,633-token document, cold | 0 | 12.45 s |
| 3 | same document again | **5,632** | **0.66 s** |

## Patch set: eight → seven

### `0033` removed

Carried `#2072` ("Reduce exact APC ownership-transfer peaks"), added 09-04
against three measured OOMs at `_clone_prompt_cache_for_apc`.

`#2072` is **still open** upstream. It was dropped anyway, because `#2182` plus
`#2262` bound the same peak from the other end: the manager sizes a snapshot
before deciding, retains at most `memory_max_bytes`, and spills anything larger
synchronously — explicitly "without a second full snapshot just to spill", which
is the sentence the patch was carried for.

The rejects decided it:

| target | failing hunks |
|---|---|
| `0.7.1` tag | 2 of 13 |
| main @ `548b09b` | **5 of 13** — `apc.py` 1/5, `apc_adapters.py` 2/3, `apc_coordinator.py` 1/2, `generate/ar.py` 1/3 |

The `ar.py` hunk fails because upstream now contains it *verbatim*:
`coordinator.store_checkpoint(self.prompt_cache, batch_idx=…)` with
`snapshot_prompt_cache_row(…, clone=False)` doing the extraction. The rest was
overwritten by the `#2262` planner rewrite.

Honestly lost with it: `#2072`'s per-layer requantise-on-restore, and the
no-copy promotion of a consumed single `KVCache` row. If the restore path ever
shows a peak again, that is the first place to look.

With `0033` gone the patch set is **entirely local work** — no cherry-picked
foreign PR left.

### `0015` reanchored into a different file

Upstream lifted `_decode_quantized_linears_fused` out of
`models/qwen3_5/language.py` into the shared `speculative/ops/linear.py`, and
the module attribute lost its prefix (`_qwen3_5_fused_decode_linears` →
`_fused_decode_linears`). The body is unchanged; the patch is the same two lines
in a new place.

Two things worth keeping in mind:

- **The switch is no longer Qwen-local.** Every model routed through
  `_target_verify_linears` sees it. Harmless — it is opt-in and off by default
  upstream — but it is no longer a per-model lever.
- **The old anchor is the trap.** Against `models/qwen3_5/language.py`, hunk 1
  (`import os`) still applies while hunk 2 does not. A `--forward` apply outside
  `apply-patches.sh` therefore leaves a tree that *looks* patched with an inert
  switch and the 9 GiB floor back — the exact failure mode `0013` sat in for six
  weeks. `apply-patches.sh` dry-runs the whole patch first and reports CONFLICT
  instead, and the start script's marker grep was moved to the new path.

There is still **no opt-out upstream**, so the floor remains the default.

Verified twice: through the entry point (default fuses and attaches
`_fused_decode_linears`; `QWEN38_FUSED_LINEARS=0` returns `None`, attaches
nothing, outputs bit-identical, max abs diff 0.0) and in production
(`mem active` 17.07 GiB after five drafter requests, against the 26.00 GiB the
fusion costs).

### The other six

Applied unchanged, `0013` included. Re-probed through the patched entry point
with the real `BatchKVCache` array mask: fused at `qL` 512, 1024 and 2048.

## Start script

- **New `#2259` guard.** Tests for the *mechanism*, not the version: if
  `_bytes_per_token` is present in `apc.py`, the defect is present. Necessary
  because the tag and the pinned commit both report `0.7.1`.
- **`0015` marker grep** moved to `speculative/ops/linear.py`. Against the old
  path it reported "MISSING" on a correctly patched tree.
- **New banner line `APC resident cap`.** Since `#2182` a snapshot larger than
  `min(8 GiB, working_set/10)` is not held in RAM but on SSD. Read from the real
  `APCManager` rather than recomputed (0.63 s at startup), because the constant
  moved once already: `#2262` rewrote the planner around it eight days after
  `#2182` introduced it. On this machine: **4.0 GiB → ~32,768 tokens per
  snapshot at two entries**, i.e. *below* the `roomy` `context_length` of 65,536.
- **The `0033` comment in the `APC_ENTRIES` block** was rewritten. "Can roomy go
  back to 3 snapshots" is no longer a question about a patch; it is a question
  about the 4.0 GiB resident ceiling, above which a third slot buys a disk
  restore rather than a warm RAM hit. Still unmeasured, still not raised.

### What was tried and reverted

Feeding the resident ceiling into `budget()`. Since the manager holds at most
`apc_cap` of snapshots in RAM, the arithmetically honest model is "one live copy
that scales, plus a flat `apc_cap` for all snapshots":

```
(40.0 − 16.0 weights − 1.5 reserve − 0.14 recurrent − 4.0 cap) / 64 KiB
  ≈ 300k tokens, clamped to the model's 262,144
```

against the ~120,654 the old formula gives. Implemented, measured in the banner,
then reverted for two reasons:

1. **The direction is wrong.** This budget is already known to be optimistic —
   on 2026-08-21 a request over 13k tokens cost +11.4 GiB where the same formula
   computed 1.6. A number 2.2× larger moves the banner toward
   `[METAL] Insufficient Memory`, which does not arrive as a clean error.
2. **It would disarm the overbooking guard**, whose job is to cut `APC_ENTRIES`
   when `_CTX_HINT` does not fit, and whose thresholds came from measurement on
   a 37.4 GiB working set. At 262,144 it never triggers again, on any machine.

The ceiling is reported as its own line instead. Revisit if eviction behaviour
is ever measured under the `#2262` planner.

## install-prereqs.sh

- `mlx-vlm` is out of `PINS` and installed **separately with `--no-deps`** from
  the git commit. In the same resolution a git requirement would let uv
  reconsider `mlx` — which is how `0013` falls inert.
- `--check` now prints the **install origin**, not just the version:
  `mlx-vlm 0.7.1  <- git 548b09b`. Without it the one number that matters here
  is invisible.

## Also new upstream, not acted on

- **`#2270`** renamed `served_tokens` → `stored_tokens` and added
  **`restored_tokens`**. That is the counter this repository has been missing:
  APC effectiveness was only measurable via `cached_tokens`, because
  `served_tokens` counted writes. Now in the README diagnostics.
- **`#2271`** ("Bound unused cache graphs during single-request decoding") reads
  like `#2210` but is not: DeepSeek-V4's rotating cache, and it explicitly
  excludes speculative decoding loops. Closes `#2042`. Not our path.
- `#2263`, `#2269`, `#2272` — further APC layout/profile work on top of `#2262`.
  The subsystem is still moving; that is the cost of this pin.

## Still open upstream

- **`#2239`** — `/v1/chat/completions` hangs intermittently (0% CPU, no tokens,
  no error) when the request carries a `tools` array, under agentic load.
  Reported on 0.7.0, reproduces with bare `curl`, `GET /v1/models` keeps
  answering. Four days old, no diagnosis, no comments. **This is our traffic
  profile** and it is not addressed by this upgrade.
- **`#2210`** — exact-APC warm hit decodes ~−35% *without* a drafter. Unchanged;
  an independent RFC reproduction landed 09-11, measured on 0.6.4. Invisible
  here because every profile runs a drafter.
- **`#2093`**, **`#1956`**, **`#1938`** — unchanged. The start script's
  `KV_BITS` + `MAX_NUM_SEQS>1` + drafter guard stays.

## Open item: the disk tier

`du` after the upgrade: **69 GB in one namespace**
(`Qwen3.8-27B-local_s4-e8629a6d`), 90 files, against a cap the start script
already trimmed from 80 to 72 GB because only 30 GB were free. The settings hash
did **not** change with the version, so those files were written by 0.7.0 and are
now served to a different planner. The on-disk schema is the same (`v4`, and the
APC self-check passes), and nothing has gone wrong in testing — but a version
change is exactly when clearing `~/.mlx-qwen38/apc` is the cheap insurance, at
the price of cold prefills afterwards. Not done here; it is an operator call.

## Recommendation

Stay on `548b09b` until the next tag. When it lands: check whether it contains
`#2262` (it must), then a plain version pin replaces the git URL, the `#2259`
guard in the start script can go, and `install-prereqs.sh` loses its separate
install step. Re-run `./measure-apc-warm-decode.py` and
`./measure-drafter-acceptance.py` then — neither was re-measured for this
upgrade, and the resident ceiling is a plausible reason for the warm-hit numbers
to have moved.
