## Why this upgrade is administrative

`0.7.2` is tagged at `a74c7de`, 29 commits past our pin. The only question that
mattered was whether the tag carries `#2262`, and the answer is stronger than
that. Diffing the tag against the commit we had been running:

```
apc.py  apc_adapters.py  apc_coordinator.py
models/base.py  speculative/  server/generation.py
→ no differences at all
```

The entire APC and speculative-decoding surface — everything the seven patches
touch, and everything `#2259` was about — is **byte-identical** to `548b09b`.
The 09-17 verification therefore still holds without re-measurement, and all
seven patches applied to `a74c7de` without fuzz or offset.

What the tag adds beyond the commit, in code we actually load: `#2291`
(Anthropic tool-call turns with no text no longer crash the chat template),
`#2260` (Chat/Responses parity), `#2320` (400 instead of a `TypeError` when a
chat model is sent to `/v1/audio/*`), `#2286` (a named `ValueError` instead of
`AttributeError` for caches that cannot batch). The rest is new models.

One behaviour change: **model discovery now runs by default**, so `/v1/models`
also lists the HF cache, and `--model-discovery` is gone (`--model-dir` replaces
it, `MLX_VLM_MODEL_DISCOVERY` → `MLX_VLM_MODEL_PATHS`). Neither flag was in use
here. The three pi instances address the model by its alias/load path, so the

### `#2310` — measured, and it costs us nothing

**Result first: the cycle is real, the fix works, and neither matters on this
profile.** Patch `0042` was written, applied, measured and then **removed
again**; the finding went to
[issue-2310-comment-draft.md](issue-2310-comment-draft.md) instead. The rest of
this section is why.

`GenerationBatch._eval_pending_state` builds a nested `append_arrays` that calls
itself. The self-reference gives the closure a cell for `append_arrays` and one
for `targets`, so `function → cell → function` is a reference cycle with every
KV array of the batch hanging off it. Refcounting cannot free it; the memory
waits for CPython's cyclic GC.

Reproduced model-free on our own install (`0.7.2`, `gc.disable()`, 12 layers ×
4 rows × 2048 × 128 bf16):

```
Runde 1: aktiv  0.47 GiB nach del
Runde 2: aktiv  0.94 GiB nach del
Runde 3: aktiv  1.41 GiB nach del
gc.collect(): 187 Objekte -> aktiv  0.00 GiB
```

Linear accumulation, fully reclaimed by one collection. With the fix applied the
same script prints `0.00 GiB` after every round, so the patch provably removes
the cycle.

The call sites bound the exposure. `extend()` needs a *non-empty* batch to merge
into and therefore never fires at `MAX_NUM_SEQS=1`; `filter()` fires when
`len(keep) < len(uids)`, i.e. `0 < 1`, **once per finished request**. The
prediction was one request's KV cache held per request until a collection runs.

That prediction is wrong, and the new
[`measure-batch-cache-retention.py`](../measure-batch-cache-retention.py) is
what showed it. Idle floor of `mem active` between requests, APC off, unique
prompts, one sample per second:

| run | idle before | after each of 6 |
|---|---|---|
| 1 slot, drafter on, stock | 15.96 | 17.12 → 17.12 (flat) |
| 1 slot, drafter on, **patched** | 15.96 | 17.12 → 17.12 (flat) |
| 4 slots, no drafter, 24 requests in 6 waves of 4, stock | 14.95 | 15.05 → 15.05 (flat) |

Identical with and without the patch, at both concurrencies. A request allocates
enough on its own to trigger generation-0 collections, so the cycle is reclaimed
long before it can pile up; the reporter's 64 GB needs batch 32 with continuous
refill to outrun the collector. The 1.16 GiB step after the first request is
**not** the cycle — it survives the patch unchanged and is something else
(allocator, retained batch state).

The consequence for the old observation that "active does not fall back between
requests" (2026-08-21): `#2310` is **not** the explanation. The floor does come
back down, reliably, at both concurrencies. That question is open again.

So patch `0042` was written, verified, measured and then removed from the patch
set. It is correct and costs three lines, but this repository's rule is that a
measurement justifies a patch, and this measurement does not. The work is not
lost: the numbers and the diff went into
[issue-2310-comment-draft.md](issue-2310-comment-draft.md), which bounds the
issue downward — upstream has the batch-32 end, not this one. Revisit if
`MAX_NUM_SEQS` is ever raised well past 4.

### `#1873` — small, and our traffic cancels

`server/generation.py`, `+63/-0`, two hunks. The regular generation path honours
disconnect cancellation; the speculative loop keeps decoding after the client is
gone. Three pi instances with interactive aborts are exactly the traffic that
hits this, and a cancelled request that keeps decoding holds its KV cache while
it burns GPU. Open since 2026-08-13, `mergeable=false` on GitHub but clean here.

Carrying it would end the "patch set is entirely local work" property that
`0033`'s removal restored on 09-17. That is a real cost — a foreign PR has to be
re-checked at every upgrade — so: measure first (how often does a cancelled
request keep running, and for how long), then decide.

### `#2318` — hold, but know it exists

`apc.py`, `+56/-7`. Counts unsatisfiable prefill reserves (`reserve_unreachable`,
`last_reserve_bytes`), warns once, and offers `APC_RELAX_UNREACHABLE_RESERVE=1`.
The 173 GB number in its report came from the pre-`PrefillMemoryPlan` estimator
that `#2262` already removed, so **we do not have that cause**. What remains is
the residual: a legitimately large reserve at long context can exceed budget plus
headroom, and `_make_room` then declines everything, silently — the `#2259`
signature without the `#2259` bug.

Our current reserve is 1.01 GB against a 4.0 GiB resident cap, so nothing is
close. **Closed unmerged today** (maintainer asked for an issue with a
reproducible example first), so carrying it means carrying a dead PR. Revisit if
`memory_skips` ever climbs with `exact_stores` flat.

### `#2261` — interesting for the disk tier, but needs a caller

`POST /v1/cache/offload` writes a finished conversation's prefix to disk and
releases the memory, refusing to release anything still held in flight. Attractive
against our 4.0 GiB resident cap. But no client of ours would call it: the pi
instances speak plain OpenAI chat completions. It would need a caller in the
watchdog or an idle sweep, which is more work than the PR. Park it.

### `#1938` — fixes the half of `#2093` we do not reach

Fixes the warm-hit crash (`AttributeError: 'tuple' object has no attribute
'shape'` when target verification meets `(packed, scales, biases)`) and gives
`BatchQuantizedKVCache` a bounded trim contract. It does **not** fix the other
half of `#2093`: `make_speculative_prompt_cache` discards the `_make_cache`
factory at `batch_size == 1`, so with a drafter and one slot `--kv-bits` is
silently ignored and the cache is never quantized in the first place. Without
that, the crash this PR fixes cannot trigger here.

Conclusion: `#1938` alone does not unlock `KV_BITS` on this profile. It would
have to land together with the factory fix, and the start script's
`KV_BITS + MAX_NUM_SEQS>1 + drafter` guard stays either way (`#2033`).

### `#1923` — redundant, confirmed by the smoke test

Adds opt-in exact-prefix APC reuse to the text-only B=1 DFlash server path.
That path already reuses: the acceptance test above ran with `SpecDec ON
(dflash, block_size 4)` and returned `cached_tokens=5348`. Whatever this PR was
needed for in August has landed some other way. Drop it from the list.

### `#2288` — not our path

Touches `turboquant.py` only. Our checkpoint is `{'group_size': 64, 'bits': 4,
'mode': 'affine'}` — TBQ is a different quantisation mode and is not loaded
here. Unrelated to our own kernel request `#2215`, which is about a packed
4-bit **KV** path.

## Also new upstream, not acted on

- **`#2324`** (merged) documents the server's draft counters, and the reason is
  a defect we inherit: `draft_n_accepted` records a round when the target
  verifies it, *before* the stop token or `max_tokens` cuts the reply, so matches
  past the end of the reply are counted and the field can exceed `predicted_n`.
  `measure-drafter-acceptance.py:190–201` computes `draft_n_accepted / draft_n`,
  i.e. with the inflated numerator. At our default (`--max-tokens 200`,
  `block_size 4`) the overhang sits in the last of ~50 rounds, so the error is
  under ~2% and the recorded findings stand — but the script should move to
  `predicted_n / draft_rounds`, which is what upstream now points consumers at.
  `#2322`, the PR that would have fixed the counter, was closed by its own author:
  it corrected `draft_n_accepted` without trimming `draft_n` for the final round,
  moving the bias from slightly high to slightly low. **The counter stays as it
  is; the correction belongs in our script.**
- **`#2307`** — Qwen3.5/3.6 MTP, +10.6% per verify cycle from 0.6.3 → 0.7.1,
  measured through oMLX (which patches the MTP path heavily), not reproduced on
  stock, different model. Weak, but our family with a drafter.
- **`#2312`/`#2314`** closed as not-a-bug: the diagnostic line "model has no
  `make_cache`" does not mean APC is off — the runtime treats such a model as
  block-eligible and builds a per-layer KV cache by fallback.
- **`#2206`** ("Rebuild speculative decoding around request caches and shared
  prefill", +3887/−26173 over 154 files) is still open. If it lands it is a
  re-cut of `0010`, `0014`, `0015` and `0041`, not a rebase.
