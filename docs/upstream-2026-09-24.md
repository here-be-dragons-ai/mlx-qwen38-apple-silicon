### `#2336` — the cause of `#2210`, and the fix

`qwen3_5/language.py` has a single-row shortcut: when the batch cache has one
row, it runs `_extract_row_cache()` + `merge()` around the forward. For every
full-attention layer that is `extract()` (a contiguous, exactly sized copy, so
the next `update_and_fetch` has to reallocate and concatenate) and `merge()`
(zeros + copy) — three passes over the whole KV prefix, per forward.

The PR's title says "after a batch shrinks to one", but the gate
(`_is_single_row_batch_cache`) matches any single-row, unquantized batch cache —
which is this server on every request. What keeps it out of normal operation is
a different condition: the shortcut requires `hidden_sink is None`, and every
DFlash and MTP verify pass passes `capture_layer_ids` (`dflash.py:104`,
`language.py:1902`), so `hidden_sink` is a list. **With a drafter the branch is
never taken**; that is the mechanism behind the 09-10 observation that the
drafter hides `#2210`. With a drafter loaded no request falls back to plain
decode either — `response_format` and `thinking_budget` raise instead
(`server/generation.py:1153`).

Isolated microbenchmark, 16 layers × 4 KV heads × 256, bf16, one new token:
10.5 ms at 8k, 29.5 ms at 26.7k, 57.9 ms at 50k per forward for the old path,
under 1 ms borrowed. (The 5-token numbers from the same benchmark were erratic
and are not quoted; the verify path does not take this branch anyway.)

End to end, `./measure-apc-warm-decode.py --prompt-tokens 28000 --max-tokens 300
--repeat 2`, 26,690 tokens, `ENABLE_SPEC_DECODE=0`, APC exact, `roomy`, one
restart per arm:

| arm | cold tok/s | warm tok/s | warm/cold | warm `mem_sum` |
|---|---:|---:|---:|---:|
| 0.7.2 as shipped | 16.02 / 15.92 | 10.42 / 10.59 | **0.658** | 30.75 / 26.80 GiB |
| + `#2336` | 16.05 / 16.12 | 16.06 / 16.04 | **0.998** | 20.58 / 20.58 GiB |

`#2210` reproduces on 0.7.2 exactly as on 0.7.0 (0.645/0.628 on 09-10), and the
PR removes it completely, together with the 26–35 GiB warm-hit excursions that
`memory.md` had flagged as unexplained. Cold decode does not move.

Correctness: a 4k-token prompt at `temperature 0`, 250 tokens — cold, warm and
a nonce'd cold run with the patch, and two runs without it, all produce the same
text (sha1 `31b90e180e38`).

With the drafter (default config, patch applied), same instrument: cold
22.12 / 22.17 t/s, warm 21.09 / 21.74 at 47.6 / 49.0 % acceptance — against
21.7 / 21.2 cold on 09-21. No regression; the warm/cold spread follows the
acceptance rate. A tool call through `qwen3_coder` parses as before.

**Why carry it**, given the default never executes it: `ENABLE_SPEC_DECODE=0` is
the documented rollback and the only way to serve `response_format` or
`thinking_budget`, and at agent context lengths it cost a third of decode and up
to 10 GiB of peak on every warm hit. The patch is one file, +40 lines, applies
without fuzz on top of the other seven, and `apply-patches.sh` will report
`CONFLICT` when upstream merges it. This ends the "entirely local patch set"
property from 09-17; that is the price.

### `#2344` — our parser, but none of the three failures bites

The Qwen3.8 chat template emits `<tool_call>\n<function=…><parameter=…>`, so the
registry picks `qwen3_coder`. Checked against the server log and all pi sessions
since 09-01 (20 sessions, 116 tool calls):

1. **Boolean property schema → call dropped** (`Invalid tool call` warning):
   zero occurrences in `server.log`.
2. **Untyped parameter → object arrives as a JSON string**: happens — four
   times, all `mcp.args`. pi-mcp-adapter declares that field as
   `Union[String, Object]` (no top-level `type`) and `JSON.parse`s strings
   itself (`index.ts:873`). Harmless. The one `mcp` error in that session was a
   wrong parameter name (`team` for `team_id`), not the parser.
3. **Unclosed `<parameter=` swallows the next one**: no `<parameter=` inside any
   tool-call argument.

Not carried. Revisit if a tool without a string-tolerant adapter takes an
untyped object parameter.
